# CNF 2026 — field and nutrient-state normalisation matrix

**Source:** Health Canada, *Canadian Nutrient File*, 2026 (relational CSV release)
**Dataset record:** <https://open.canada.ca/data/en/dataset/1b6139bd-ed7e-4043-bc28-ff00e10f3109>
**Retrieved and inspected:** 2026-10-21, from `cnf_fcen_all-files-data_2026.zip`
(SHA-256 `f5faad8977ee6bbdd9d69c8649077cacd87d8658ad200509a4047db1e29edcdd`).

> **Engineering specification. Not a licence clearance and not a clinical
> approval.** No CNF data is ingested by this milestone.

**Every number in this document is produced by
`research/measure-cnf-2026.mjs`, which is committed, and the summary it
generates is committed as
`research/fixtures/cnf-2026-nutrient-amount-summary.csv`.** The figures can be
re-derived rather than trusted.

## 1. Which CNF release is authoritative

**The published 2026 relational CSV release is the authority.** The online
search tool and the `food-nutrition.canada.ca` API are *not* substitutes: they
expose different field names and a legacy dataset.

| Concept | CNF 2026 CSV column | CNF API field | Same? |
|---|---|---|---|
| The value | `Nutrient_Amount` | `nutrient_value` | renamed |
| Sample count | `Observations` | `number_observation` | renamed |
| Provenance code | `Nutrient_Source_Code` | `nutrient_source_id` | renamed |
| Nutrient | `Nutrient_Code` | `nutrient_name_id` / `nutrient_web_name` | renamed |
| Uncertainty | `STD_Error` | `standard_error` | renamed |
| Food | `Food_Code` | `food_code` | renamed |

The API additionally exposes `Refuse Amount` and `Yield Amount` endpoints; the
CSV release has no refuse/yield tables, so "refuse" and "yield" are **not**
available in the CSV release and must not be silently substituted from the API.

**Rule:** an importer reads the CSV release. If the API is ever used, it is
adapted into the CSV field names first, and the adaptation is itself tested.

## 3. The missingness rule

**A nutrient is unknown for a food exactly when there is no row for that
(food, nutrient) pair in `Nutrient_Amount.csv`.**

Measured on the 2026 release:

- 565,409 rows over 5,993 foods × 172 nutrients = 1,030,796 possible pairs
- **density 54.9 %** — the table is sparse
- rows per food: minimum 14, median 94, maximum 162
- **zero empty `Nutrient_Amount` cells** — a present row always carries a number
- 199,662 rows carry the value `0`

| Situation | Meaning | Normalised state |
|---|---|---|
| no row for (food, nutrient) | the source did not report this nutrient | `unknown`, no value |
| row present, value non-zero | a value, with the quality its source code describes | per §5 |
| row present, value `0` | a zero the source stands behind | `documented-zero` |
| row present, source code `12`, value `0` | an *assumed* zero | `documented-zero` |
| row present, source code `12`, value non-zero | **a conflict in the source data** | see §5.1 |
| row present, amount blank | no amount published | `unknown` — **never zero** |

**`Observations` is never used to decide whether a value exists.** It records
the number of analytical observations and is empty or zero for every value that
was not laboratory work. That is a statement about the *evidence*, not about
*presence*.

### 4.1 The figures, reconciled

Across the whole release:

| Population | Rows |
|---|---|
| Zero values with no positive observation count | **149,873** |
| Non-zero values with no positive observation count | **219,204** |

So a rule that discarded every value without a laboratory observation count
would have deleted **149,873 legitimate zeros and 219,204 legitimate non-zero
values** in this release alone.

**The source-code 12 conflicts, broken down exactly:**

| Code 12 (assumed zero) | Rows |
|---|---|
| total | **65,887** |
| value = 0 | **65,805** |
| value ≠ 0 — the conflicts | **82** |
| of the 82, with a positive observation count | **2** |
| of the 82, without a positive observation count | **80** |
| value blank | 0 |

These are the figures `research/measure-cnf-2026.mjs` prints, and they agree
with the committed `research/fixtures/cnf-2026-nutrient-amount-summary.csv`.

> **Erratum.** An earlier draft of this document claimed that "174" rows were
> a subset of the 82 conflicts. **That claim is wrong and is withdrawn.** No
> population of 174 rows exists in this release, and the 82 conflicts break
> down as 80 without a positive observation count and 2 with one. The earlier
> figure was a mis-derivation and should not be carried into any downstream
> document or review.

## 5. Nutrient-source code → value state

Implemented in `research/normalize.ts` as `CNF_NUTRIENT_SOURCE_QUALITY` and
pinned by `tests/m2-normalization.test.ts` against the published
`Nutrient_Source.csv`.

| Code | Published description | State | Why |
|---|---|---|---|
| 0 | No change from USDA | `inherited` | The value is carried over. The CNF does not state the quality of the value it carries over, so **"no change from USDA" does not establish that the value was laboratory analysed**. Claiming `analysed` here would over-claim 236,117 values. |
| 1 | Levels changed to meet the Canadian regulations | `calculated` | A regulatory adjustment of an inherited value. |
| 2 | Calculated from data other than USDA | `calculated` | |
| 3 | Analyzed in a Canadian government lab | `analysed` | The publisher says so. |
| 4 | Calculated from USDA data | `calculated` | |

| 7 | Analyzed in a Canadian product (non-government lab). Documentation complete. | `analysed` | The publisher says so. |
| 8 | Value of food created for the Nutrition Canada Survey | `estimated` | A formulated food, not a measured one. |
| 9 | From the label declaration | `estimated` | A manufacturer-declared value. |
| 10 | Derived from scientific literature | `estimated` | |
| 12 | **Nutrient value is an assumed zero** | `documented-zero` when the amount is zero; **see §5.1** otherwise | |
| 14 | Provisional data | `estimated` | |
| 15 | Imputed from data other than USDA | `imputed` | |
| 16 | Calculated field | `calculated` | |
| 17 | Calculated from analytical Canadian data | `calculated` | |
| 50 | Calculated from literature for surveys only | `calculated` | |
| 51 | Calculated using a recipe | `calculated` | |
| 81 | International database | `inherited` | Another dataset. Its own quality is not restated here, so **this does not by itself prove the value was laboratory analysed**. |
| 82 | Danish Food Composition Databank | `inherited` | as above |
| 83 | Fineli, Finnish food composition database | `inherited` | as above |

**An unrecognised code** keeps the amount, is marked `estimated`, and is
**flagged for review** (`needsReview`), rather than being given a quality it
has not earned. The code table is the extension point; adding a code is a data
change that must be reviewed.

### 5.1 Source code 12: an assumed zero, and the conflicts

Code 12 says *"Nutrient value is an assumed zero"*. It is a statement about a
**zero**, so it can only be applied to a row whose amount actually is zero.

| Row | Normalised | Why |
|---|---|---|
| code 12, amount `0` | `documented-zero`, value 0, no flag | The normal case: 65,805 rows. |
| code 12, amount ≠ 0 | value **kept as published**, state `estimated`, `needsReview: true`, review reason recorded | A conflict in the source data. The amount must not be silently replaced with zero, and the value must not be automatically claimed to be analytically measured. **82 rows.** |

The 82 conflicts carry small amounts — for example 0.001, 0.002, 0.003,
0.005, 0.006, 0.011, 0.012, 0.015, 0.02, 0.021, 0.04, 0.048, 0.05, 0.07,
0.109, 0.14, 0.15, 0.286, 1.0 and 7.71 g — which look like a source
designation that was not updated when a small amount was recorded. They are
**not** silently corrected: the raw amount and the source code are preserved
and the row is flagged, so the conflict can be investigated rather than
overwritten.

`tests/m2-normalization.test.ts` pins this with two conflict rows (a 0.02
amount and a 7.71 amount) and a blanket assertion that **no fixture row ever
has its published amount replaced**.

## 7. Nutrient mapping onto the app's 19 keys

The app's key order and set are fixed in `src/core/foods.ts`:
`calories, protein, carbs, fat, fibre, sugar, satFat, sodium, potassium, calcium,
iron, magnesium, zinc, vitaminC, vitaminD, vitaminB12, folate, vitaminA,
cholesterol`.

The app's units are `kcal`, `g`, `mg`, `mcg`. CNF's `Nutrient_Unit` is a word:
`Gram`, `Milligram`, `Microgram`, `kilocalorie`, `International Unit`,
`Niacin Equivalents`. A unit map is therefore required, and **one CNF nutrient
must never be mapped**: vitamin D also exists in International Units
(`VITD_IU`, code 324) alongside micrograms (`VITD`, code 328). Mixing them
would be wrong by a factor of 40.

## 8. Serving measures

CNF gives household measures through `Measure_Weight_Conversion.csv`
(`Food_Code`, `Measure_Type_Code`, `Measure_Code`, `Measure_Weight_Conversion`)
joined to `Measure_Name.csv` and `Measure_Type.csv`.

- The app's serving model is `{ label, grams }`. A CNF measure becomes
  `{ label: measure description, grams: 100 × conversion factor }`.
- **`Measure_Type_Code` 3 (Refuse) and 9 (Yield) must be handled, not dropped.**
  A refuse measure is the inedible portion; a yield measure is the edible
  yield. The app's serving grams are the *edible* portion, so a yield measure
  is the correct basis and a refuse measure is not a serving at all. The CSV
  release has no refuse/yield tables, so refuse data is **unavailable in the
  authoritative release** and must not be taken from the API.
- The app already appends `"100 g"` and `"1 oz"` to every food. CNF supplies
  its own household measures, so the merged serving list must be de-duplicated
  the way `fromRow` does today.

## 9. Taxonomies

CNF's `CNF_Food_Group_Code` (23 groups) is a **different taxonomy** from the
USDA group codes the app's `dishTraits` and `dishIngredients` read off
`row[2]`.

**Rule:** the USDA group codes keep their meaning. A CNF food must not be fed
into the USDA-group allergen heuristic, because the code spaces are not
interchangeable. A taxonomy mapping (CNF group → app group) is a separate,
explicit, reviewed table, and until it exists, allergen inference applies only
to USDA-sourced foods.

## 10. The normalisation rules, in one place

```
row absent                        -> { state: "unknown" }
row present, amount blank         -> { state: "unknown" }        // never zero
row present, amount not a number  -> { state: "unknown", needsReview: true }
row present, source code 12,
        amount 0                   -> { state: "documented-zero", value: 0 }
row present, source code 12,
        amount != 0                -> { state: "estimated", value: amount, needsReview: true }
row present, source code unknown  -> { state: "estimated", value: amount, needsReview: true }
row present, amount 0             -> { state: "documented-zero", value: 0 }
row present, otherwise            -> { state: quality(source code), value: amount }
```

with `Observations` and `STD_Error` carried through as evidence, **never** as a
presence test, and the source code and its published description always
preserved alongside the value.

A value is only ever **displayed as a number** when its state is one of
`analysed`, `calculated`, `imputed`, `estimated`, `inherited` or
`documented-zero`, and when it carries no `needsReview` flag it is *settled*.

Implemented in `research/normalize.ts` and pinned by
`tests/m2-normalization.test.ts` (20 deterministic tests, no network).
