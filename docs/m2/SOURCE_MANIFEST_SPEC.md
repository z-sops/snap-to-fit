# Source manifest specification (M2-0)

**Purpose:** make every byte of nutrition data traceable, reproducible and
verifiable — so that "which dataset, which version, which licence, which
checksum" has one answer that is machine-checkable.

**Status:** specification only. No manifest is generated and no dataset is
ingested by this milestone.

---

## 1. What a manifest is

A **source manifest** is a committed JSON file that records, for every input
that feeds a generated data artefact:

- what the input is (source id, dataset, version),
- where it came from (exact URL, retrieval date),
- what licence it carries and the commercial-use verdict,
- the **SHA-256 of the exact bytes used**,
- and what artefact those bytes produced, with that artefact's own checksum.

The manifest is the link between a licence decision and a byte in the app. If
the bytes change, the checksum changes, and CI fails until the change is
reviewed and the manifest is updated.

## 2. Files

| Path | Purpose | Committed? |
|---|---|---|
| `docs/DATA_SOURCES.md` | Human-readable registry: licence, evidence, verdict, status. | Yes |
| `data/manifest.json` | Machine-readable manifest: ids, versions, URLs, checksums, artefact links. | Yes |
| `data/manifest.lock.json` | Generated by the verification step; the *actual* checksums observed for a run. | No — produced in CI and compared |
| `data/sources/<source-id>/` | Downloaded source bytes, per dataset. | No — fetched on demand, never committed |

Source bytes stay out of the repository unless the licence explicitly permits
redistribution **and** a size decision says it is worth it. The CNF's small
reference tables are the only exception so far, and they live under
`research/fixtures/`, not `data/sources/`, because they are research inputs
rather than build inputs.

## 3. Schema

```jsonc
{
  "manifest_version": 1,
  "generated_at": "2026-10-21T00:00:00Z",
  "sources": [
    {
      "id": "usda-fdc",
      "name": "USDA FoodData Central",
      "publisher": "USDA Agricultural Research Service",
      "dataset": "SR Legacy",
      "version": "April 2018",
      "landing_url": "https://fdc.nal.usda.gov/",
      "download_url": "https://fdc.nal.usda.gov/download-datasets/",
      "licence": {
        "name": "CC0 1.0 Universal",
        "url": "https://fdc.nal.usda.gov/api-guide/",
        "commercial_use": "permitted",
        "evidence_url": "https://fdc.nal.usda.gov/api-guide/",
        "evidence_quote": "USDA FoodData Central data are in the public domain and they are not copyrighted.",
        "checked_on": "2026-10-21",
        "next_review": "2027-04-21"
      },
      "files": [
        {
          "path": "ABBREV.txt",
          "url": "<exact download URL>",
          "sha256": "<hex>",
          "bytes": 0,
          "retrieved_on": "2026-10-21"
        }
      ],
      "produces": [
        {
          "artefact": "src/data/usda-foods.json",
          "builder": "scripts/build-foods.mjs",
          "builder_version": 1
        }
      ]
    }
  ],
  "artefacts": [
    {
      "path": "src/data/usda-foods.json",
      "sha256": "f2b1a828ce58ee0731d076938b483c16c194bc276294a99d7263cc137fd060a2",
      "bytes": 1420723,
      "builder": "scripts/build-foods.mjs",
      "source_ids": ["usda-fdc"],
      "dataset_version": "SR28 / SR Legacy April 2018"
    }
  ]
}
```

### 3.1 Field rules

- `id` — lower case, hyphenated, stable for ever. It is written into the
  generated catalogue, so it must never change once shipped.
- `licence.commercial_use` — one of `permitted`, `prohibited`, `unresolved`.
  **`unresolved` blocks the build.** A source with `unresolved` may not be
  downloaded by a build script, and the build must fail if a dataset it
  consumes is not `permitted`.
- `files[].sha256` — of the **downloaded bytes**, before any extraction or
  transformation. A file that is not byte-reproducible (a rolling "latest"
  download) must be pinned to a dated URL.
- `artefacts[].sha256` — of the generated bytes, so a rebuild that changes
  anything is visible in review.
- `licence.next_review` — a `permitted` verdict is not a permanent fact. When
  the date passes, CI reports the source as overdue.

## 4. Reproducibility rules

1. **Pinned inputs only.** A manifest entry names a dated file, never
   "the latest release".
2. **Checksum in, checksum out.** A build that downloads a file whose SHA-256
   is not in the manifest fails immediately.
3. **Deterministic builders.** The same input bytes must produce the same
   output bytes. This is enforced by a golden test: the builder is run against
   a checked-in fixture and the output is compared byte for byte.
4. **No network in the app build.** The catalogue is committed. CI never
   downloads food data to run the test suite; it only verifies checksums of
   what is already committed.
5. **The manifest is reviewed like code.** Changing a checksum is a data change
   and goes through the same review as a source change.

## 5. Verification procedure

```
npm run data:fetch      # download pinned inputs, verify SHA-256 against data/manifest.json
npm run data:build      # run the builders, write artefacts + data/manifest.lock.json
npm run data:verify     # compare manifest.lock.json with data/manifest.json and the committed artefacts
```

`data:verify` is the gate. It fails when:

- a downloaded file's checksum differs from the manifest,
- a committed artefact's checksum differs from the manifest,
- a source consumed by a builder is not `permitted`,
- a licence is past `next_review`,
- a builder's output is not byte-identical to the committed artefact.

## 7. What this milestone does not do

- It does not download the CNF into the repository as a build input.
- It does not generate `data/manifest.json`.
- It does not change `scripts/build-foods.mjs` or any production file.
- It does not change the shipped catalogue.

The scripts named above are the **planned** interface. They are part of the
M2-2 work package, and the naming is fixed here so the reviewers can see the
shape of the gate before it is built.
